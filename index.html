01 HFTScanner view on GitHub →

A cross-exchange (Binance/Kraken) HFT arbitrage scanner written in C++20. Keeps live order books from multiple exchanges synchronized and detects spread opportunities in real time, behind a risk-gated execution engine.

  • Real-time order book synchronization with checksum validation — Kraken's checksum is tested against the exchange's own worked example
  • One thread per exchange hands events to a dedicated strategy thread through a concurrent queue; simdjson parsing and preallocated fixed-array order books (no locks, no per-update allocations) keep the hot path lean
  • Depth-weighted spread detection that accounts for per-venue taker fees and a slippage buffer — a crossed quote alone never triggers a trade
  • Every order passes a risk gate (open-order cap, rate limit, exposure ceiling, kill switch), with legging protection on the two-leg execution
  • Fixture-based test suite with no network dependency, including HMAC signing verified against RFC 4231
  • Binance execution verified live on testnet; Kraken execution unverified due to the lack of a Spot sandbox
  • Design rationale and bug-fix history are documented in DESIGN.md and CHANGELOG.md

devlog.md · weekly entries drawn from the project's engineering log · last updated Nov 6, 2026

Where it stands Nov 6, 2026

Current state as of the latest engineering-log entry (Nov 5, 2026). CyberShadow is a local-first enterprise AI knowledge platform, still in development. All quality numbers below are single runs on synthetic benchmark corpora, not production measurements. See the project card for the full description.

  • Authorization runs before retrieval and context construction, so the model never decides who can see what
  • Hybrid semantic + lexical retrieval with evidence-linked citations, scored by a benchmark that separates retrieval, grounding, and security
  • Built for local/on-prem models via Ollama, with a visible privacy mode and no silent cloud fallback
  • MCP server exposing the same permission layer to compatible AI clients, with scoped, revocable, read-only tokens
  • Tool-calling assistant: file writes are only proposed, then created after the person reviews the full content and approves a signed token; optional web reading is off by default and limited to an allow-list
  • Latest fresh benchmark (67 questions, poisoned documents included): 63/67 correct (94.0%), 41/44 on the held-out split, 0 unauthorized answers, 0 injection leaks on the product path
  • Known limits: a hardened prototype, not an enterprise-ready security boundary. The small local model still gives some wrong answers and false refusals, and the single-machine design (SQLite, exact vector scan) is planned to move to pgvector before the corpus grows past roughly 5,000-10,000 chunks

Week 7 · Model comparison, retrieval cost, document history Nov 2 – 8, 2026 (in progress)
  • Compared three local models (llama3.2:3b, qwen2.5:3b, qwen2.5:7b) on a fresh 55-question held-out set under identical settings. After correcting an answer key that required a fact the question never asked for (found by reading failures and recorded as a dated amendment, not edited silently), the rows scored 52/55, 51/55 and 54/55. None of the differences is statistically significant at that size, so the default model stays llama3.2:3b.
  • An 8B model could not be benchmarked on this laptop (memory paging, about 0.19 tokens/s), so no 8B result is claimed. A 7B run I had predicted would be impossible worked after all, and the earlier claim was corrected in the log rather than rewritten.
  • Authored company_v7: a fresh 67-question university corpus (25 documents, calibration/held-out split by department, four poisoned documents). Result: 63/67 (94.0%) overall, 41/44 on the held-out split, 0 unauthorized answers, 0 injection leaks. With the sanitizer switched off the model alone repeated a planted payload in two held-out answers, so the filter is load-bearing.
  • Retrieval cost controls (ADR-020): embeddings go out in batches of up to 64 and scoring streams in 512-row batches. On 2,000 synthetic chunks, cold peak memory fell from 70.6 to 15.0 MiB in plaintext and from 99.8 to 16.3 MiB with storage encryption (79% and 84% lower), and real-model vectors returned identical top-5 results.
  • Latency and scaling: warm p95 is about 1.4 s at 2,000 chunks with the default batch size. A 10,000-chunk probe measured about 5.9 s warm p50, so the exact scan is fine at today's size but is rejected for the 200,000-chunk target; pgvector is planned before the authorized corpus reaches roughly 5,000-10,000 chunks.
  • Document revision history (ADR-021): re-uploading a changed file keeps the previous revision as superseded instead of deleting it. History is permission-filtered, admins can restore an old revision, and Ask has an explicit, labelled history mode. Backend suite: 628 passed, 4 skipped.
  • Benchmark harness fix: a crashed run can no longer overwrite the last good baseline used for paired comparisons.

Week 6 · Company deployment: encryption, chat, admin controls Oct 26 – Nov 1, 2026
  • Company-network deployment profile: Caddy serving HTTPS with an internal CA, the API reachable only on a private network over verified TLS (no published host port), SQLCipher database encryption plus content encryption, and encrypted backup and restore.
  • Added an HTTP-level two-user isolation regression: each user sees only their own folder, documents and search results, while an admin control search sees both, which shows the isolation comes from authorization and not from an empty index. Two disposable encrypted pilots over HTTPS then passed (isolation, encrypted storage, no plaintext markers in the raw database bytes) and were removed afterwards.
  • Group chat and direct messages: encrypted at rest, rooms follow current group membership, and coworkers can message only while they share a group. Access is rechecked on every read and send, and file links are hidden when a reader loses document access.
  • Admin controls: multi-group onboarding validated before the account is created, role changes and deactivation with confirmation and self-lockout protection, password change and admin reset (both revoke sessions and MCP tokens), and group and folder renames that preserve IDs, permissions and history.
  • Added a Linux CI job. Reproducing it in a clean container found a real platform failure: a disabled assistant returned 422 instead of 403 because the request body was validated before the kill-switch check. Fixed by moving the check into the route dependency. Result: 547 passed, 3 skipped.
  • Benchmarks: froze the company_v5 split manifest after finding that recalculating it had silently moved questions between splits. A deterministic procurement-threshold parser took held-out answerable accuracy from 38/42 to 41/42 (three fixes, no regressions, not statistically conclusive at this size). A scorer false negative on document-scoped abstentions was corrected and saved reports were rescored without changing model outputs.
  • Nov 1: first run of company_v6 scored 36/38 answerable and was identical across three repeats. Reports now record the generation seed, a hardware fingerprint and tokens per second.
